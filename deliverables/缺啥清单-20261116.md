## 一、最急的 5 条（不定就卡住主链路）

### 1. Qwen 真实调用方式与 5 个官方模型 id 映射
- **缺什么**：5 个官方模型各自真实的 API id 与 endpoint、判题返回字段（对错／思路／答案的字段名与拆题口径）。
- **流程**：F1 主链路（拍题→判题→思路→答案）。
- **原型／PRD 有没有**：没有。PRD 只说“官方 API 主链路（Qwen）已验证”，没给 endpoint、没给各模型 id、没给返回格式；JT Lite 2.0 的真实 API id 在 PRD／原型里根本没出现。
- **怎么绕过去的**：`judge.py` 里产品模型名 → DashScope 兼容接口 model id 的映射表只是猜测（JT Lite 2.0 → `qwen-vl-max`、Qwen 3.8 → `qwen-vl-plus`，其余照名字直填），endpoint 暂写 `https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions`，prompt 要求模型输出 `{"results": [...]}` JSON。无 `QWEN_API_KEY` 时整个 F1 停在“大模型”阶段，返回明确的 `model_not_connected`，不编假答案。
- **状态**：**已定（部署时定）**——2026-11-16 浩爷在房间里已定：Qwen 真实调用方式与 5 个模型映射部署时再说，现在不用管，stub 留着，别追这条。骨架保持 stub 模式，F1 仍停在“大模型”阶段返回 `model_not_connected`，等部署时再接真实调用。

### 2. 申请卡的包形式与批卡回传通道
- **缺什么**：批卡后是服务端主动推给终端，还是终端下次连接拉取；推送通道本身是什么（长连接／轮询／第三方推送）；申请消息是消息包还是数据包。
- **流程**：F3 求助／领取、F4 申请消息。
- **原型／PRD 有没有**：PRD 6.7 流程 2 明说“包的形式（消息包还是数据包）未定”“学生端拿到卡的回传通道未定”。
- **怎么绕过去的**：骨架做成“服务端记账＋客户端拉取”：批准发卡直接改余额，学生端下次 `POST /cards/check` 即看到新余额；申请消息推送只进本机内存队列（`GET /push/pending` 可查），不等真实通道。原型“在第 13 屏时不弹条”是客户端展现规则，服务端不硬编码。
- **已定（2026-11-16，Nyx：我们自己研究定）**：不建服务端推送通道，全部拉取——网关无法主动建连到终端（板子在内网、无公网地址，手机端无推送服务），现有架构全是 HTTP 请求／响应。批准发卡是数据包（服务端记账＋终端下次调 A3 查卡同步余额）；申请通知是消息记录＋拉取（家长端下次调 B2 或 `GET /push/pending` 看到新申请后弹条）。骨架现有的“服务端记账＋客户端拉取”做法就是定稿做法，不用改。卡规则／服务器配置下发同一口径：终端下次连接拉取（见第 10 条）。

### 3. 处理五阶段真实进度推送
- **缺什么**：推状态用 WebSocket／SSE／轮询中的哪一种、每阶段的事件名与字段。
- **流程**：F1 处理页（上传→网关→大模型→NLP→下发）。
- **原型／PRD 有没有**：PRD 6.2 步骤 8 明说“真实进度靠网关推状态，接口未定”；原型是固定时间依次点亮（演示）。
- **怎么绕过去的**：骨架不做真实推送。`POST /solve` 同步调用，判题完成才返回 job；五阶段字段只在 job 里按实际走到的步骤打点，客户端靠轮询 `GET /solve/{job_id}` 看状态。
- **已定（2026-11-16，Nyx：我们自己研究定）**：轮询，不建推送通道——网关是纯 HTTP 服务（骨架 Python 标准库，无 WebSocket 服务端），五阶段状态已在 job 里（`stage`／`stage_index`），终端在处理页轮询 `GET /solve/{job_id}`，1 秒一次、最多 60 秒，超时 50401；五阶段名 `uploading`／`gateway`／`model`／`nlp`／`delivering` 已定。骨架现有的同步＋轮询做法就是定稿做法，不用改。

### 4. 家庭组建立方式与注册成功下一步
- **缺什么**：两件事。① M15 虚拟组提议（注册后先给虚拟家庭组、有成员加入时再固化、ID 不变）采纳与否；② 注册成功后是再输一次管理密码，还是直接进管理首页。
- **流程**：F6 管理（注册／登录）。
- **原型／PRD 有没有**：① PRD 3.6、附录 A：提议，未拍板。② 原型代码是 `goTo(10)`（第 11 屏输管理密码），即刚设完六位管理密码、成功后又要输一次才能进管理首页（缺口 L3）；合理性可疑。
- **怎么绕过去的**：骨架原来按原型走——注册时即建真实家庭组；现按定稿改：注册时建**虚拟**家庭组（`status: "virtual"`），首个新成员加入时翻为已固化、ID 不变；一个人先注册就能直接拍题、绑终端、用卡；先注册的人默认管理员。注册／登录成功后仍返回 `next_step: "verify_admin_password"`，再输一次管理密码进管理（② 按原型 v155 原样走，不变）。
- **已定（2026-11-16）**：① 虚拟组提议采纳；② 再输一次管理密码进管理首页（按原型 v155 原样）。

### 5. 16 位设备 ID 的生成办法与 L1 三重撞号的新码
- **缺什么**：各平台取哪个标识、哈希算法；L1 三个撞号位置（板子 7 屏、手机 7 屏、手机 15 屏终端 3，都是 `1040059832773436`；终端 4 是 `...3437` 连号）改哪处、改成什么。
- **流程**：F5 设置／配网／连通、F6 终端绑定。
- **原型／PRD 有没有**：PRD 5.3 明说“各平台具体取哪个标识、哈希算法，待技术方书面确认，未定”；撞号是原型注释与实际码值自相矛盾（注释说“拉开大差距、不连号”，实际就是连号）。
- **怎么绕过去的**：骨架只做校验＋唯一性（16 位纯数字、首位类型码、重复直接 409），不生成 ID、不做哈希；扫码绑定只解析载荷里已有的 16 位数字。撞号已替原型改码（见下）。
- **已定（2026-11-16）**：生成办法——第 1 位类型码（1 嵌入式、2 安卓、3 苹果、4 鸿蒙，0 其他），后 15 位设备号；嵌入式由 Wi-Fi MAC 转换，安卓／苹果／鸿蒙拿不到 MAC 的用其唯一标识在本地稳定哈希转成 15 位纯数字，原始串号不上传；真实设备按这个办法生成不会撞。撞号新码（Nyx 定）：板子 7 屏留 `1040 0598 3277 3436`，手机 7 屏改 `2864 1907 5238 6419`，15 屏终端 3 改 `1762 9048 3157 8260`，终端 4 改 `1938 2756 8041 5692`；三处二维码载荷与热点名已同步改（手机 7 屏热点名 `JianTi-2864190752386419`，二维码载荷为 JianTi-2864190752386419（带前缀，与板子同一格式）；旧码只含后 15 位是原型笔误，已顺带纠正）。

## 二、接口未定（对齐文档 M13 清单，骨架按最合理的方式先写了，都在清单里标着）

### 6. 判题接口字段与返回格式
- **缺什么**：`/solve` 的字段、返回格式、拆题口径（见第 1 条）。
- **流程**：F1。
- **原型／PRD 有没有**：PRD 6.2 只定了“压到 8MB 以内发网关 `/solve`”，字段未定。
- **怎么绕过去的**：请求是 raw JPEG body（不是 multipart、不是 JSON 包图片），头 `X-Terminal-Id`＋`Authorization: Bearer`；响应是一个 job：`{job_id, status, stages, correct, thinking, questions[], error}`；答案字段默认不出现，只有解锁的题才在 `questions[i].answer` 里出现；一张照片多道题时 job 内用 `questions` 数组按题拆（`question_index` 从 0 起）。

### 7. 空白题判定口径（已定，Nyx 2026-11-16 22:38）
- **定稿**：空白题按识别失败走——job `failed`＋`failure_reason: no_question`，终端提示“这张里没有题目”，回取景器重拍；不判题、不给思路、不直达答案（PRD v5.5＋手册 §2.5＋接口文档 106 行）。代码已对上：`gateway.py` 判题失败分支 `failure_reason` 就是 `no_question`。
- **流程**：F1（空白卷绝不直接给答案是 PRD 第 0 章红线）。
- **原缺口**：“空白”的判定口径（无作答笔迹 vs 全部空白），以及服务端要不要再加一道空白检测。
- **怎么绕过去的**：骨架层面不单独判断空白题；模型 prompt 要求“只判最终结果”，空白卷无最终结果可判时模型应返回空 `results` → 走 `no_question`（原 `no_question_detected` 写法统一为接口文档的 `no_question`）。

### 8. 申请单接口字段
- **缺什么**：申请单的字段名、状态机细节。
- **流程**：F3、F4。
- **原型／PRD 有没有**：PRD 只定了创建／待批／批准／撤回由服务端统一管，没给字段。
- **怎么绕过去的**：申请单 `{id, family_id, terminal_id, requested{grant_type,value}, status}`；状态 `pending → approved | rejected | withdrawn`，只有 `pending` 能批／拒／撤回；创建时 `requested` 可空（家长批时才选按张／按倍、再填数字，PRD 3.5 原话）。

### 9. 记录上传接口
- **缺什么**：记录由终端上传还是服务端直接记。
- **流程**：F1、F3（第 13 屏三组数与详情日志）。
- **原型／PRD 有没有**：M13 列了“记录上传接口未定”。
- **怎么绕过去的**：骨架没有单独的记录上传接口——记录由服务端在每次真实事件发生时直接写（solve／deduct／advance／application／grant），客户端不上传；`GET /records` 只读服务端已入库的记录，`GET /usage` 三组数全部由记录表汇总。第 13 屏三组数与详情日志的口径（日期补零、各列对齐、来源写终端／成员）是展现层格式，服务端只给原始记录。

### 10. 卡规则与服务器配置下发方式
- **缺什么**：下发是推送还是终端下次连接拉取。
- **流程**：F5、F6。
- **原型／PRD 有没有**：PRD 6.7 流程 5 明说未定。
- **怎么绕过去的**：骨架假定“板子下次连接时拉取最新配置”，`POST /config/server` 只保存到服务端，返回 `push_mode: "stub"`，本次不向板子推送。
- **已定（2026-11-16，同第 2 条）**：终端下次连接拉取，不主动推。骨架现有的做法就是定稿做法。

### 11. 申请发送失败、识别失败的分支落点
- **缺什么**：网关真拒收、模型真没读出题时，终端停在哪一屏、给什么提示、能不能重发／重拍。
- **流程**：F1、F3。
- **原型／PRD 有没有**：没有。原型里没有这两个分支（对齐文档 M19 已列，缺口 C2 核对属实）：申请点完只写“申请已发送。”，没有失败重发；拍完处理页五步恒亮，没有“没拍到题／识别失败可重拍”的分支。
- **怎么绕过去的**：骨架只给错误码与落点，不编分支界面——模型未接通／调用失败／返回无法解析时 job 状态为 `failed`（`model_not_connected`／`judge_failed`），不编任何思路／答案；照片里没有可判的数学题时 `no_question`；申请发送失败（42201）留在领取页、可重试、不谎称“已发送”。失败不自动重拍、不自动重试。

### 12. 推送通道（申请消息）

### 15. 其余接口自定项（已标在骨架 ASSUMPTIONS.md，不再展开）
- 改每日张数后今日剩余的算法：`今日剩余 = 新每日张数 − 今日已用 + 今日已预支 + 今日已批`，下限 0（A2）。
- 批准“按倍”的发卡数：每日张数 × 倍数值（A3）。
- 自有服务器地址格式：只要求非空字符串，不校验 IP／域名格式（A15）。
- 限流数值：通用每 IP 每分钟 120 次，`/solve` 每终端每分钟 10 次，超了 429（A19）。
- 密码哈希参数：PBKDF2-HMAC-SHA256，12 万次迭代，16 字节随机盐（A10；“存哈希”是已定项，参数自定）。
- 额外端点 5 个（A20）：`POST /cards/config`、`POST /applications/{id}/reject`、`POST /users/*` 三个、`GET /push/pending`、`GET /lockscreen`——清单里的模块没有这些入口就接不上，不加是缺功能，加了要明说。
- 二维码载荷与热点名格式已统一为 `JianTi-<16 位>`：扫码绑定接受纯 16 位数字与 `JianTi-<16 位>` 两种载荷（兼容旧码）；热点名格式是终端展现问题，服务端不管（A22，对应 M4）。

### 22. 三端状态各玩各的（服务端收拢方案）
- **缺什么**：服务端接通后三端联调验证。
